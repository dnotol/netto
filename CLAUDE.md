# CLAUDE.md

## Project

Netto tells a Belgian SRL owner-director how to pay themselves for the year so that the most money reaches their own pocket: the split between director pay and dividends, costs and benefits in kind, advance tax payments. It runs locally only; there is no production and no hosting yet.

**Docs map.** Each has one job.

| Where | Holds |
|---|---|
| `CLAUDE.md` (this file) | Instructions only: what an agent must do, must not do, or would otherwise get wrong. No status, no history, no domain spec. Edit it when a slice changed a convention, an architecture rule or a gotcha. |
| Notion, « Netto Development » | Every unit of work (Work Items, User Stories), the product contract (the « Goal & scope » page: what v1 is and is not) and the Lever catalogue (one page per fiscal lever, with its official sources). There is no backlog file, and what shipped is the git history. |
| `official-docs/` | The official documents the rules are taken from, as they were when read, each with the income years it applies to and its status (`INDEX.md`). Its `README.md` says how to file one. |
| The River Map, an Artifact ([link](https://claude.ai/artifact/C2gkexviNGUUMzDbpaqaEX)) | The river as decided: a diagram of the whole river and one of each mechanism that reaches across modules or layers, each module with what it asks and where its money goes, the buckets, the dated rules the river follows and what is still open. |

**Always current: the River Map and the official documents.**

- **The River Map is updated in the slice that changes the river** (a module, a bucket, a rule, a figure it quotes), in place at the same URL: read it first (`Artifact read`, then `path: "index.html"` for its file, whose publish skeleton is stripped before republishing), add a dated rule, and bump its date and the `main` commit in its footer.
- **Every complex part of the domain has a clear diagram on the River Map, as current as the code**: the whole river, and each mechanism that reaches beyond one card or one layer (a company car: its costs off the profit, its benefit in kind taxed as pay, what Corporate tax adds back and tests, the muddy pocket). It is drawn while the mechanism is analysed, before its first slice, marks what is not decided yet as such, and is redrawn in the slice that changes the mechanism, never left showing a river the code no longer runs.
- **`official-docs/` is checked for newer editions regularly**: at the start of every slice that touches a layer, for the documents that layer's rule sets cite (a newer coordinated article on Fisconetplus, a new indexation notice, a law or programme law published since), and each year once the next income year's amounts are published. A newer edition is filed (downloading needs the operator's go) and the old one marked superseded, and the rule set that cites it is checked against it in the same slice.
- **Every Artifact that states Netto's rules or figures is faithful to `official-docs/`**, the River Map first: each rule and amount it shows is the one the current documents give for its income year, and it changes when they do.

## Where work comes from

**Work is operator-picked, one slice at a time, never self-started.**

The tracker is Notion: the « Netto Development » page, holding **Work Items** (the executable unit, typed Task / Bug / Technical, filed under an `Area`: Tax engine · Web app · Content · Plumbing · Intendance), **User Stories** (a user-facing outcome grouping several items; a technical item with no story is normal) and the **Lever catalogue**. `Status` runs Backlog → Selected → Doing → Done, and **`Selected` is the operator's pick**. A lever is in scope only once the operator sets it to `In v1`.

- **Read Notion freely**, starting with « Goal & scope » before planning anything.
- **Write narrowly.** While implementing: set `Doing` / `Done` on the item being worked, create a new item at `Backlog` for something discovered mid-slice, and edit « Goal & scope » where the slice changed the contract. When the task is plainly analysis, writing the related pages is the work. Never re-prioritise, re-file or reorganise unless asked.
- **A session is self-contained.** If a slice ends unfinished, say what is done and what is left in a comment on its Notion item.

## Methodology

- **One slice = one session = one feature branch**, carrying focused commits and fast-forwarded onto `main` when the slice is done (`git-branching`).
- **Work is named, never numbered**: a Work Item is cited by its title.
- Plan first on any non-trivial task and wait for operator approval before writing code. Minimal diffs: no refactoring outside the current task.

## Stack

- .NET 10, Blazor Web App with WebAssembly interactivity, Aspire 13 AppHost as the local launcher.
- MudBlazor 9 in `Netto.Web.Client` for every component, and `Microsoft.Extensions.Localization` for the interface text.
- Test projects carry BOTH the native MTP runner (`xunit.v3.mtp-v2`) and the VSTest bridge (`Microsoft.NET.Test.Sdk` + `xunit.runner.visualstudio`), referenced once in `tests/Directory.Build.props`, so Rider still discovers tests: **remove neither**.

- `MessagePack` is a security pin in the AppHost only (see its csproj). Drop it once Aspire's own graph resolves a patched version, never earlier.

## Architecture

- **Projects and dependency direction**: `Netto.Web.Client` → `Netto.Core`; `Netto.Web` → `Netto.Web.Client`; `Netto.AppHost` → `Netto.Web`; tests → `Netto.Core`, `Netto.Web.Client`. Never the reverse.
- **`Netto.Core` is the tax engine and stays a plain library**: no ASP.NET Core dependency (`CoreDependencyTests` fails if one appears) and nothing the browser runtime cannot run (`SupportedPlatform=browser` raises CA1416; fix it, never suppress it). That is what lets the engine move behind an API later without a rewrite.
- **Every page is WebAssembly and none is prerendered.** `App.razor` sets the render mode once, on `<Routes>` and `<HeadOutlet>`, so the server never runs a component and a user's figures only ever exist in the browser. Pages live in `Netto.Web.Client` and carry **no** `@rendermode` line; declaring one inside the already-interactive tree throws. Never add prerendering, a server-side component or a server endpoint that receives user figures without the operator deciding it.
- **`Netto.Web` only serves the app.** If Netto ever gets an API, it goes there, not in a new project.
- **No tax rule outside `Netto.Core`.** A component growing an `if` about tax behaviour means that logic belongs in Core. Core returns data and error keys, never display text; the page turns a key into English.
- **The engine follows the law's order of computation** (Notion, « Engine architecture »): layer calculators composed by one year simulation (`YearSimulation.Run(Scenario)`), and each module card of the river reads its steps, tagged by layer and taxable event, instead of calculating on its own; a new income year is a rule set, a lever is scenario inputs plus a rule in the layer it touches plus its steps. What the company pays the director besides pay (the vouchers, the expense allowances, the home office rent) comes off `Scenario.ProfitBeforeDirector`, revenue less running costs, before the split shares the rest (`YearSimulation.ProfitBeforePay`); what the company cannot deduct of it is added back to its taxable income (`YearResult.DisallowedExpenses`), and a lever's steps join the ledger only when it is used, so a year without it keeps its steps. The plausible swap seams are the regional tax and how director pay is paid. A search across pays (`SplitSearch`) runs `YearSimulation.Level`, the year's figures without its steps or the next 1,000, never arithmetic of its own, with every other input held, the advance payments among them; `SplitSearchTests` holds each pay it draws to `Run`. The moves Netto recommends from Today are found the same way (`MoveSearch`): each kind of move has a finder (`IMoveFinder`: the split's best pay; the company's and the director's advance payments that cancel each surcharge by the first deadline not yet past on the date the search is given, from the browser's clock through `TimeProvider`; the eco and sport/culture vouchers at their maxima; the home office rent at the cap once its facts are given; never the flat expense allowances, worth nothing to a director without an advance ruling Netto cannot see) proposing its move from where the plan stands, the move that adds the most is taken and the others asked again on top of it, until none adds a euro, and a move the engine refuses or that leaves less than the reserve is never taken; every gain is the difference of two `YearSimulation.Run`s, so the moves' gains sum to the plan's pocket less Today's. A move of a kind already taken (`Move.Kind`: its value, a payment's deadline) replaces it in its line, which adds both gains (`Move.After`: a payment adds to the earlier one), so the card shows one line per value. A new kind of move is a `Move` record, its finder and its words on the card (`MovesCardText`).
- **A thing the company puts at the director's disposal is a module of its own behind one plain contract** (Notion, « Engine architecture », decided 2026-10-22). The company car lives in `Netto.Core/CompanyCar/` (its facts `CarFacts`, `CarRules` per income year, `CarCalculator`: the benefit's CO2 percentage and age bands, the deduction rate by the car's acquisition period (`CarRules.DeductionPeriods`), the part of the costs art. 66 §3, 3° keeps deductible, and the add-back), tested on its own, and its card, view models and texts in `Netto.Web.Client/River/CompanyCar/`. It hands the year one result, `BenefitInKind` (`Netto.Core/BenefitsInKind/`): the flat-rate benefit taxed as pay, what the director pays the company for private use, the yearly costs, the part the company cannot deduct with the share of the benefit it adds back, and the muddy pocket; a laptop or a phone will give the same. `YearSimulation` composes it beside the vouchers, the allowances and the rent, and is the only engine code that names the car: the costs less the contribution come off `ProfitBeforePay` into the muddy pocket (`Track.Muddy`, `YearResult.MuddyPocket`), the contribution leaving the pocket for the company; the benefit goes into `GrossToNet` as `benefitInKind`, taxable pay never paid in cash (INASTI, the income tax, the key formula's withholding and the assessment rise with it; the net in pocket and the company's cost of the pay leave it out), and into `CorporateTaxCalculator` as `flatRateBenefits` with the pay that counts it; what the company cannot deduct joins `YearResult.DisallowedExpenses`. What the company cannot deduct of a car's costs is what its rate leaves out beyond the part equal to the benefit taxed and the contribution, which stays deductible up to the costs; it joins `BenefitInKind.NotDeductible` beside the 17%/40% add-back, both on a car deducted at 0% (operator, 2026-10-22), and a car not deducted in full lists it as a step of its own (`car_costs_not_deductible`). Nothing car-specific in DirectorPay, PersonalTax, SocialContributions or CorporateTax: the boundary is a convention checked at review, not a test. A step that rests on more texts than its own names them in `Step.AlsoCites`; the amounts a step cites are the ones the calculator used, handed back with its result (`CarResult.Co2Amounts`, `DeductionAmounts`), and a rule set's dates (a deduction period's start, a fake hybrid's first year) are plain `DateOnly` values beside its amounts, as an age band's month is.
- **Rules come only from official, current sources** (tax administration, Moniteur belge, INASTI), each amount with its source and income year. An amount that is not published yet is marked as such, never guessed; a rule set that borrows the latest published amounts records the year they were set for (`MunicipalRates.RatesIncomeYear`). The Lever catalogue holds the research; the document an amount is read from is filed in `official-docs/` (downloading one needs the operator's go), and a rule set cites only documents current for its income year. Each `Source` names that file in `Document`, the path `INDEX.md`'s *File* column gives, and `SourceDocumentTests` fails when an amount of a rule set, or a source its steps cite, points to a document `INDEX.md` does not list as `current` for that income year. A static step source (`PersonalTaxRules.IncomeTaxScale`) is held to every year the steps run for, so it has to become per year once the next year's rule sets exist; a year that borrows a document is in its *Applies to* (`official-docs/README.md`). A CIR 92 amount cites the administration's coordinated article for that income year on Fisconetplus (« Article 130, CIR 92 (revenus 2026) »), which carries the year's indexed amounts; not an SPF summary page, which can lag a reform (the rates page still showed the pre-reform 2026 tax-free amount in October 2026), nor Justel's CIR 92, frozen since 2002. A card's list of conditions (`VoucherRules.Conditions` and the like) is held to the same documents: a condition whose text is not filed waits for it rather than showing unsourced.
- **One rules record per layer, one instance per income year** (`SocialContributionRules.IncomeYear2026`, `PersonalTaxRules.IncomeYear2025`, found through `For(year)`). Every amount is a `RuleAmount` carrying its `Source`, and rates are fractions (20.50% is `0.205m`). A new year is a new instance, never an edit of last year's.
- **The director's monthly withholding is its own rule set** (`WithholdingRules.IncomeYear2026`, the key formula's steps in `WithholdingCalculator`, each line rounded as the SPF simulator's formula chain rounds it). Its amounts cite annex III as decreed on 11.12.2025 (« Règles 1er janvier 2026 ») and its method the key formula: the coordinated annex III on Fisconetplus shows the latest amendment's value of n° 32 (3,089.63 from 1 November 2026), not January's. The rule set dates the rules it holds (`RulesFrom`) and the ones it does not model yet (`UnmodelledRulesFrom`), and the statement flags the months from that date. The pay statement (`GrossToNetResult.Statement`) and the balance on the assessment (`GrossToNetResult.Assessment`, by `AssessmentCalculator`) are records beside the ledger, not steps. Another income taxed with the pay, the home office's net rent, goes into `GrossToNet` as `otherIncome`: the pay's own figures (its steps, its net, its statement) stay the pay alone's, as art. 158 takes the pay for the surcharge; `GrossToNetResult.OtherIncomeTax` is what the rent adds (the tax on the total less the pay's, the credit for low earned income it takes away, the surcharge that lost credit adds), and `AdvancePayments`, `Assessment` and `NextThousand` are on the whole income (Tax-Calc T13 and T14). `TaxPrepayments.Withheld` is null for the key formula's withholding, which `GrossToNet` derives from the pay before the surcharge; `IncomeTaxAdvancePaymentCalculator` refuses a null.
- **Round where the administration rounds**: `Money.RoundToCent` (half away from zero) on each line its calculation detail shows rounded, not once at the end. INASTI bills four rounded quarters; Tax-Calc rounds the flat-rate costs, the basic tax, the federal share, the Walloon tax and the tax credit for low earned income each on its own.
- **Eligibility is declared by the user, never decided by the engine**: Core takes what it cannot see as a status (VVPRbis shares and their distribution, a small company the reduced corporate rate is open to, its first four tax periods and its first three financial years, both set in the river by one choice of the company's financial year, the director's first three years of a first self-employed activity, who pays the director's social contributions, `ContributionsPaidBy`, the days worked that the meal vouchers match, the share of the home let to the company, and what Netto cannot see of a company car: whether the company pays the private fuel or charging, what drives the car, its CO2 as registered or that none is, the date it was ordered or leased, whether a plug-in hybrid is a fake one with its matching car's CO2, and whether a natural-gas car is under 12 fiscal horsepower) and shows its conditions. A car with a combustion engine whose CO2 is not given is refused, never taken at an example (operator, 2026-10-22). When the company pays the contributions on the director's behalf they are taxable pay, deducted as the director's own: the split's pay stays the gross on the payslip, the company's cost (gross plus contributions) comes off its profit, and the art. 215 minimum pay is tested on the taxable pay. A condition on the scenario's own figures is the engine's to test, because the levers move those figures: the minimum director pay that keeps the reduced corporate rate, tested on the taxable pay with the benefits in kind counted, and those benefits, after the director's contribution, within 20% of it (strictly; art. 215 al. 3, 5°, in the first four tax periods too).
- **User data stays in the browser**: browser storage and file export, no accounts, nothing sent to a server. Saved plans outlive the code, so they are stored in a versioned format of their own (`PlanStorage`, never `RiverInputs` serialised as it is) and read strictly: a plan is read as it was saved or marked unreadable, never filled with defaults, and a document that cannot be read is copied aside before anything is written over it. A new input of the river is a new field of the format and a new `PlanStorage.Version` (`RiverInputsShapeTests` fails until it is). `PlanStorage.Version` is 2 since the company car; a version-1 document is read in its own shape (`StoredInputsVersion1`), each plan as saved and without a car, and written back as 2. The car's engine, CO2, order date and statuses joined format 2 without raising it, format 2 not having left the car's story branch, so a plan saved by the car's first build does not open (operator, 2026-10-22); any later new input raises the version.
- **The site is one river at `/plan`** (« Goal & scope », « How the site is organised »): module cards (`River/*Card.razor`) under the bar of buckets, each editing its part of one `RiverInputs` and drawing its view (`River/ModuleViews.cs`) of the one `RiverInputs.Run()`, so the river always adds up. The page holds the inputs (`RiverState`, kept for the tab) and hands each card the engine refusal it owns (`RiverErrors`). The plans the user saves sit in a panel from the bar (`River/PlansPanel`, `SavedPlans`): saving adds one and never replaces another, the river opens on the plan last opened (`RiverState`), and the plan starred « Today », the user's current setup, is the baseline every gain is measured against: the bar and each plan show its net in pocket less Today's (`BaselineGain`), never comparing a river that starts at the pay with one that starts at the company's year. The gain stays in cash; beside it, the bar and each plan say what the muddy pocket holds more or less than Today's (`BaselineGain.MuddyDifference`). Opening a plan over changes no plan holds (`SavedPlans.HasUnsavedChanges`, the example counting as the plan when none is opened) asks first. A new module is a card, its view model and its texts; a condition set elsewhere shows on the card it acts on, never as a link back up. A module the user may leave out (the levers) is optional: it joins or leaves the plan from the Composition menu in the bar (`River/CompositionMenu`), so it is also an `OptionalModule` value, a flag of `PlanComposition` (a positional input of `RiverInputs`), a gate in `RiverInputs.Scenario` that hands the engine its `None` while it is out, the menu's texts and its card's `RemoveLabel`. What is out neither shows nor counts, so every figure traces back to a card on screen, and its values are kept for when it comes back; setting a value never adds a module, and only applying a lever's move from the moves card does. The lever cards before the split (Vouchers, Expense allowances, Home office rent, Company car) run one under the other, each passing on what it leaves to the next, its view model summing the engine's steps. The split also draws the engine's search (`RiverInputs.SearchSplit()`), which runs the year at about a hundred pays and takes about 50 ms in the browser, so the page runs it again only when an input other than the pay changes (`RiverInputs.SameBesidesPay`). The moves card at the top of the river (`River/MovesCard`, `MovesView`), folded while no plan is starred Today, runs `MoveSearch` on the plan starred Today, once per Today, and is the one place a recommended move is applied: the split's curve shows the best pay and weighs it, with no button of its own; and « Apply » sets the river's values to a move's (`MovesView.Apply`: a payment move sets the payment by its deadline to Today's plus the move; a lever's move adds its module to the plan, the one action that does, since the user asked for it), Today staying as saved. The search runs `RiverInputs.MoveScenario`: Run's scenario, with the home office's facts kept while Rent is out of the plan and its rent at nothing, which the engine counts as no rent.
- **Every input of the river says where its value comes from** (`InputOrigin`: yours, default, derived, example). Defaults exist only for rates and statuses, never for money: an amount the user has not given is the opening example's and says « example », and a module whose amounts are cleared is skipped, the river starting below it. The plan's composition is not a figure and has no origin: the example holds no optional module.
- UI copy is English only, and interface text lives in resource files so a translation can be added later (« Goal & scope »): a `.resx` beside each component (`Pages/Home.resx` for `Pages/Home.razor`), read through an injected `IStringLocalizer<TComponent>`. No interface text inline in a `.razor` file; the wordmark « Netto » is a brand, not copy. A misspelt key fails silently (the page shows the key), so read the page in the browser after adding one. Keys a component builds from the engine's keys (`Drain_social_contributions`) go through a helper beside it (`River/RiverText.cs`, `DirectorPay/PaySlipText.cs`) that a test (`RiverTextTests`, `PaySlipTextTests`) runs against the `.resx`. A block several cards show (`Steps/StepDetails`, `River/DrainList`, `River/OriginChip`, `River/ConditionList`, `River/Disclosure`, `River/InfoBubble`) is a component with its own `.resx` and helper, so its texts cannot drift between cards. A term of art explained in a bubble is marked `[term]` inside its sentence in the `.resx` and drawn through `TermSentence`, its meaning keyed by a `*Text.*Term` constant; whoever translates a text keeps its brackets.
- **The front page makes no claim the product does not keep yet**: no amounts, no results, no testimonials, and an « In development » label until the planner ships.

## UI

- **One dark theme**, `Layout/NettoTheme.cs`: gold primary on a warm black. Its colours are literal hex because MudBlazor parses each one to derive hover and darker variants, and the `:root` block in `Netto.Web/wwwroot/app.css` mirrors them as CSS variables for hand-written CSS. **Change both together.**
- **Gold is an accent, not decoration**: the main button, active states (hover, focus), small icons and, later, key figures. No gold gradients, no glows, no animated gold. On a site about keeping more money, they read as a get-rich scheme and cost the trust the product sells. Eyebrows, icon tiles and borders stay neutral.
- **Fonts are self-hosted** (`Netto.Web/wwwroot/fonts`: Inter for text, Fraunces for headlines). Never link a font service such as Google Fonts: it sends every visitor's address to a third party, which breaks « nothing leaves your browser ».
- **`MudBlazor.min.css` loads before `app.css`** (`App.razor`), so `app.css` wins at equal specificity. Scoped `.razor.css` reaches the elements MudBlazor renders only through `::deep` from an element of the component's own markup.
- Razor gotcha: **a component is always generated `public`**, so a type it takes as a parameter (`StepDetail`, `MunicipalityChoice`, `Drain`) has to be public too, or the build fails on inconsistent accessibility. An internal view model stays internal: the component takes the engine's result and builds the view itself (`PaySlip` takes a `GrossToNetResult`).
- Razor gotcha: **a `string` parameter takes its attribute as text** unless the value starts with `@`: `Error="Refused"` passes the word « Refused », `Error="@Refused"` the property. Parameters of any other type are read as C#.
- **A card shows the plan, and says the rest on demand, one pattern each.**
  - Every card folds (`River/Fold`): the whole header row is a button inside the heading with `aria-expanded`, a chevron at its right, down when folded and up when open, the summary shown in both states. A fold inside a card (its conditions, its pay slip and sources) is the same at level 3. A fold is the viewer's preference, remembered in the browser (`Folds`, localStorage key `netto.folds`, through `BrowserStorage`), never part of `RiverInputs`; a fold's `Name` is kept from one version to the next, or a viewer's folds are forgotten.
  - Settings rarely changed sit behind `River/Disclosure`, folded to one line that states their values (`River/SettingsViews.cs`, tested against the card's `.resx`), naming the origin only of what Netto assumed. « Change » stays a word, since it opens fields to edit; a refusal on a field inside keeps it open.
  - Help is an info bubble (`River/InfoBubble`), given through `Help` on `RiverField`, `Disclosure` or `ModuleCard`. A bubble never holds what the plan needs to be read right: refusals, conditions, a field's bounds, caveats and amounts stay in sight. Its trigger is a button of its own, never inside a fold's header, a `MudButton` or a checkbox's label, and its text is the trigger's description (`aria-describedby`), never a live region. `Netto.Web/wwwroot/info-bubble.js` places the open one and closes it on Escape or a press outside.
  - An action that changes the plan (« Remove from your plan ») is a word at the bottom of the open card, never an icon in its header.
- **A drain list shows only the lines that move money** (`River/DrainLines.Shown`): a line of €0.00 is left out on every card, while its step stays in the ledger and in the card's sources. A drain of steps carries their details (`Drain.Details`), which its bubble shows.
- **A share is a division of the engine's own figures, made in a view model** (`Shares.Of`, none where the base is nothing). The bar's reach is the pocket out of what leaves the company, since what the company keeps is still the director's and never counts as lost; each card's summary ends on one rate, worded once by `ModuleCard` (`ToYou`, `PassesOn`); a drain line or a pay slip row carries its share of what its card receives, and a remainder passed on to the next module none. Whole percents at a glance (`Formats.WholeShare`), one decimal in the funnels (`Formats.Share`).
- **The bar's live region is the river's only announcement** (`bucket-bar__live`, out of sight): what reaches the pocket and, once a plan is starred « Today », its gain over it, or that a refused amount leaves no figure, once the river has been still for a moment (`BucketBarAnnouncement.Settle`), so a dragged slider is read out once. Nothing else in the river is a live region that changes while an input moves, and no bubble or menu sits inside one.
- **The river meets WCAG 2.2 AA on a desktop; a new control is checked against it in the browser.** One gold focus ring for the site, in `app.css` (`--netto-focus-ring`, `--netto-focus-offset`, on `:focus-visible`); a component draws its own only when it needs another, and text fields keep MudBlazor's gold frame. Text is at least 4.5:1 on its background; the frames of fields and chips and a slider's track at least 3:1 (`LinesInputs`, mirrored as `--netto-line-input`); `TextDisabled` draws disabled controls only. A slider carries `aria-valuetext` in `Formats`. Headings run h1 for the page, h2 for a card, h3 for a fold or a disclosure inside it, h4 inside a detail view; a `RiverField` without `For` is a group named by its label. A page's skip link goes in `MainLayout`'s skip-link section (`MainLayout.SkipLinkSection`).
- MudBlazor gotcha: **a `MudExpansionPanel`'s header is a `div` with no role, name or state**, and takes no attributes, so a screen reader hears an unnamed focusable. A fold is `River/Fold`, or the button rows of `Steps/StepDetails` for a list of steps whose open state is not remembered.
- MudBlazor gotcha: **a `MudNumericField` clears a refusal passed as `Error`**: its own validation resets `Error` after each edit, and MudBlazor applies a parameter only when it changes. A number field of the river is a `River/RiverNumericField`, which sets the refusal again after validating and carries the engine's message as its error text for screen readers, out of sight beside the card's alert.
- MudBlazor gotcha: **a `MudButton` centres its content.** A button drawn as a row (a fold's header) sets `justify-content: flex-start` itself.
- MudBlazor gotcha: **a `MudSelect` is named by its `InputId`.** A select of the river sets `InputId` to its `RiverField`'s `For`, so the field's label names the combobox.
- Razor gotcha: **a `@for` loop variable captured by a child component's content is read after the loop has ended** (a `MudSelectItem` per month drew month 13 and threw). Loop with `foreach`, whose variable is fresh each time.
- Razor gotcha: **whitespace is dropped next to a C# block and kept between two inline elements.** A space before an `@if` or after a `@foreach` disappears (a heading read « Company year€120,000.00 »), so a needed space is CSS or `@(" ")`; a newline between two inline elements draws a space (« flat charges : »), so elements that must touch go on one line.
- MudBlazor gotcha: **a field redraws its text from its value only once it has lost focus.** A field whose value the river bounds (the split's pay, what the dividend keeps) is taken when the field is left, without `Immediate`, or the typed amount stays on screen beside the bounded one.
- **A chart stretches with its card**: an inline SVG with `preserveAspectRatio="none"`, its lines kept to their width by `vector-effect: non-scaling-stroke`, and what must keep its shape (a dot, the axes' labels) as HTML placed over it in percentages (`River/SplitCard`). A small `MudSlider`'s thumb is 2px wide, only scaled up to draw, so a plot above one sits 1px inside the slider's ends for each pay to line up with its thumb.
- **The bar of buckets sticks under the site header by the header's height** (`River/BucketBar.razor.css`, `4.25rem` and its border from `Layout/MainLayout.razor.css`), and `app.css` keeps a control reached with Tab below both (`html:has(.bucket-bar)`'s `scroll-padding-top`, the header plus the bar with its line on Today, with its own values below 1,200 px, where the bar's buttons go under its figures, and on a phone). **Change the three together**, and measure the bar's height in the browser when it gains a line or a button. With a company car the muddy pocket is a fifth bucket after the pocket (`BucketsView.Muddy`, only while a car counts): five across, three below 960 px, two on a phone (`bucket-bar__buckets--five`), and `app.css` gives that bar its own scroll padding below 960 px and on a phone.
- **Numbers go through `Formats`** (€50,000.00, built on the invariant culture), and MudBlazor inputs get `Culture="Formats.Culture"`. Never set the app's culture in `Program.cs`: Blazor loads only the browser language's ICU data and the app fails to start on a culture change. A rule amount is formatted by its key's suffix (`Formats.RuleAmount`: `_rate` a percent, `_multiplier`, `_coefficient`, `_grams` an emission in g/km, anything else euros), so the key of a rate or a share ends in `_rate`. A car's CO2 percentage or deduction rate keeps its decimals (`Formats.Percentage`: 9.75%, 61.6%).
- **A numeric field the engine validates carries no `Min`/`Max`**: MudBlazor would clamp the value silently and the engine's error key, with its message, would never show.
- **Nothing is prerendered, so the page is empty while the runtime downloads.** `App.razor` shows a splash, and `app.css` hides it as soon as `.netto-app` (the layout's root) exists. A layout without that class leaves the splash on screen.
- Blazor gotcha: **a link to `/#section` from another page lands at the top**. Blazor scrolls to a fragment only on a same-page link; after a cross-page navigation, `blazor.web.js` resets the scroll to the top once the new page has rendered, undoing any scroll towards the section. So the header's section links render only on the front page, and the front page scrolls to one of its own sections itself when opened directly (`/#principles`), for a fixed list of ids, because the fragment becomes a CSS selector.

## Testing

- **Test-first in `Netto.Core`.** `Netto.Tests.Unit` mirrors Core's folders, plus `Architecture/` for the guards on the project graph, and runs without Docker.
- **A card's or a page's own logic is a view model, tested first too**: plain C# in `Netto.Web.Client` (`internal`, visible to the tests) that turns the engine's result into what it draws (`RiverInputs`, `BucketsView`, `River/ModuleViews.cs`), tested under `Netto.Tests.Unit/WebClient/`. The `.razor` file only binds it. The view model never decides a tax outcome; it selects, orders and scales the engine's steps.
- **The year charges both advance-payment surcharges unless the scenario prepays**: the company's on its corporate tax, and the director's on the income tax on the pay when too little of it was withheld or paid in advance. The river's example prepays nothing by the company and withholds on the pay as the key formula says (`TaxPrepayments.AsWithheld`, decided 2026-10-20), so it shows the company's surcharge and the balance left on the assessment. A test about something else prepays, so its figures stay those of the layer it is about: `YearSimulationTests` and `SplitSearchTests` default to a `Prepaid` amount by 10 April, `GrossToNetTests`, `YearSimulationTests` and `SplitSearchTests` to a `Withheld` amount beyond any tax, and the web tests to a prepaid copy of the example that withholds a given amount.
- **A decimal can be a negative zero** (`0m - 0.00m`). `ShouldBe` and record equality take it for 0, but `ArgumentOutOfRangeException.ThrowIfNegative` rejects it and a drain reads it as money coming back (`decimal.IsNegative`), so only the browser showed the crash: guard with `ThrowIfLessThan(x, 0m)`, return a plain `0m` for what moves nothing, and test a zero line with `decimal.IsNegative`.
- **No real figures in the repository.** Tests use made-up cases. The operator's own figures live under `/local/`, which git ignores; never copy them into a test, a commit message or Notion.
- A personal-tax expected value comes from a Tax-Calc run on the same inputs, and the test names the income year it covers. For a year Tax-Calc does not cover yet, it is derived from the official amounts and the test says so.
- **The monthly withholding has no Tax-Calc check**: Tax-Calc takes it as an input (code 1407). Its expected values are derived from the key formula and cross-checked against the formula chain of the SPF simulator's « Dirigeants d'entreprise » sheet, read out of the xlsx (no Excel on this machine runs it), and the test says so. The balance on the assessment is held to Tax-Calc's « SOLDE » line, the one before the special social security contribution (T12, 2026-10-20).
- **Tax-Calc** (the SPF's anonymous simulator, latest income year only) is driven in the browser, and each submission needs the operator's go. « Encodage rapide » takes codes 1001 (single: a box in cadre II, which its validation links to), 1400 (director pay), 1405 (own contributions), 1407 (withholding: required whenever 1400 is filled, 0 is fine) 1437 (withholding on the dividends exempt up to 833, listed as a refundable element) 1571 to 1574 (the director's advance payments, one per quarter), and 1109 and 1110 (the non-indexed cadastral income and the gross rent of a building let to a company for its professional use, cadre III, A, 5, a); cadre I needs a postal code, the municipal rate and a birth date. A director's benefit in kind has no code of its own: it goes into 1400 with the pay, as the 281.20 sums them (T15, 2026-10-22). Entering a code again adds a second line instead of replacing the first: start a new form (« Accéder à Tax-Calc ») for each run. Read « Détail du calcul »: the tax credit for low earned income is the line « Faibles revenus d'activités » under « Crédits d'impôt », and « Majoration pour absence ou insuffisance de versement anticipé » and « Bonification » detail the advance-payment surcharge and bonus line by line, the surcharge on the tax recomputed on the director pay alone (« Revenus soumis à majoration »). Its question on the special social security contribution defaults to « Oui »: answer « Non », since a self-employed person in main occupation does not owe it (`official-docs/social-contributions/`). The 2026-10-19 runs found no field for it in the anonymous form; its line comes after the ones Netto compares, so read those.

## Definition of done

A slice (or any task) is done only when ALL of:

1. `dotnet build` clean (no warnings) and `dotnet test` green, run from the repo root.
2. The acceptance criteria of the slice's Notion item are met and demonstrated in the running app (browser-verified through the AppHost), not only in tests.
3. Docs are true again: « Goal & scope » edited where the contract changed, any convention here that the slice changed updated, the River Map updated where the river changed, its diagrams with it, `official-docs/` holding the current edition of every document the slice's rule sets cite, and the Notion item moved to `Done`.
4. The branch's commits are listed (contents + messages) and the fast-forward onto `main` is operator-approved. Pushing, once a remote exists, needs separate explicit approval.
